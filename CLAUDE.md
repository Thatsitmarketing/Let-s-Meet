# Let's Meet

Eigene Terminbuchung von That's it. Marketing nach dem Vorbild von Calendly: eine zentrale Buchungsseite für das Büro, einbettbares Widget und ein Backoffice für das Team, komplett im Branding von That's it. Marketing.

**Zentrale Buchung (seit 2026-10-27):** Gebucht wird nie bei einzelnen Mitarbeitern, sondern immer beim Büro `info@thatsit.marketing`. Das Büro ist ein Eintrag in `nutzer` mit `ist_buero = 1`. Ihm gehören Terminarten, Verfügbarkeit, Ausnahmen, Google Kalender, Webhook und alle Buchungen. Teammitglieder melden sich mit ihrem eigenen Konto an und verwalten das Büro gemeinsam (Middleware setzt `locals.gastgeber` = Büro, `locals.nutzer` = angemeldete Person).

## Kunde und Ziel

* Kunde: That's it. Marketing, Gelsenkirchen (intern genutzt, Ansprache per du)
* Ziel: Calendly ersetzen. Interessenten buchen Erstgespräche und Calls direkt, ohne Mailpingpong
* Primäre Conversion: abgeschlossene Buchung auf `/` bzw. `/{terminart}` oder im eingebetteten Widget
* Branding Quelle: „Thats it Marketing Branding Guide“ (Google Drive, Ordner Marketing intern, Version 1.0, 2026)

## Stack und Befehle

| Bereich | Wahl |
| --- | --- |
| Framework | Astro 7, `output: 'server'` |
| Hosting | Cloudflare Workers mit Static Assets (Adapter `@astrojs/cloudflare` 14 unterstützt nur noch Workers, nicht Pages) |
| Datenbank | Cloudflare D1 `terminethatsitmarketing` (ID `26aa6845-79a5-419a-9f2d-8ee308d6f37e`), Binding `DB` |
| Mail | Resend über die HTTP API |
| Spamschutz | Cloudflare Turnstile, Honigtopf, Mindestzeit |
| Kalender | Google Calendar API (OAuth, freeBusy, Termine mit Meet Link) |
| QR-Codes | `uqr` (Kodierung), SVG und PNG baut `src/lib/qr.ts` selbst im Worker |
| Cron | Cloudflare Cron Trigger alle 10 Minuten (Arbeitsabläufe wie Erinnerungen, Löschfristen, Abgleich Google Kalender) |
| Runtime | Node 24, pnpm 10 (`.nvmrc`, `engines`, `packageManager`) |

```bash
pnpm install
pnpm db:migrate:local      # D1 lokal anlegen
pnpm dev                   # http://localhost:4321, Daemon: astro dev stop | logs
pnpm build                 # baut nach dist/client und dist/server
pnpm astro preview         # gebaute Version lokal in workerd
pnpm check                 # Typprüfung (braucht TypeScript 6, nicht 7)
pnpm db:migrate:remote     # Migrationen auf die echte D1 anwenden
pnpm deploy                # build, Migrationen remote, wrangler deploy
pnpm deploy:cloudflare     # Deploybefehl für Cloudflare Workers Builds (nach pnpm build)
```

**Arbeitsregel Migrationen:** Neue Migrationen immer direkt selbst auf der D1 `terminethatsitmarketing` ausführen (Cloudflare MCP `d1_database_query`, Anweisung für Anweisung) und danach in `d1_migrations` vermerken (`INSERT INTO d1_migrations (name, applied_at) VALUES ('000X_name.sql', CURRENT_TIMESTAMP)`), damit der Deploybefehl sie nicht doppelt ausführt. Nicht auf den Merge oder den Deploy warten. Vorher mit `SELECT name FROM d1_migrations` prüfen, was schon eingespielt ist.

Lokale Geheimnisse liegen in `.dev.vars` (nicht eingecheckt). Vorlage mit allen Namen: `.env.example`.

### Deployment als Cloudflare Worker (nicht Pages)

Ein Pages Projekt funktioniert mit diesem Setup nicht (liefert 404), weil der Astro Adapter einen Worker baut.

1. D1 Datenbank ist angelegt und in `wrangler.jsonc` verknüpft (`terminethatsitmarketing`)
2. Cloudflare Dashboard, Workers & Pages, Erstellen, Worker, Repository importieren: `Thatsitmarketing/Let-s-Meet`
3. Workername exakt `let-s-meet` (muss zu `name` in `wrangler.jsonc` passen)
4. Buildbefehl `pnpm build`, Deploybefehl `pnpm run deploy:cloudflare`, Produktionsbranch `main` (empfohlen, der alte Branch `claude/affectionate-pasteur-q3ennq` ist veraltet)
5. Unter Einstellungen, Variablen und Geheimnisse als Secret setzen: `SESSION_SECRET`, `SETUP_TOKEN`, später die übrigen aus `.env.example`
6. Der Deploybefehl wendet die Migrationen auf die D1 an. Falls dem Build Token die D1 Rechte fehlen: einmal lokal `pnpm db:migrate:remote` ausführen
7. Custom Domain `letsmeet.thatsit.marketing` im Worker hinterlegen und `SITE_URL` in `wrangler.jsonc` prüfen
8. `/app/setup` aufrufen, mit `SETUP_TOKEN` das erste Admin Konto anlegen. Danach ist die Seite gesperrt

### Google Kalender einrichten

1. Google Cloud Console: Projekt anlegen, Google Calendar API aktivieren
2. OAuth Zustimmungsbildschirm (intern oder extern), Scopes `calendar.events` und `calendar.freebusy`
3. OAuth Client vom Typ Webanwendung, Weiterleitungs URI `https://letsmeet.thatsit.marketing/api/google/rueckruf` (lokal `http://localhost:4321/api/google/rueckruf`). Die URI wird aus der Adresse im Browser gebildet (`url.origin`), daher jede genutzte Domain eintragen, auch `https://let-s-meet.<konto>.workers.dev/api/google/rueckruf`, solange die Custom Domain noch nicht läuft. Sonst meldet Google `redirect_uri_mismatch`
4. `GOOGLE_CLIENT_ID` und `GOOGLE_CLIENT_SECRET` als Secret setzen
5. Unter Backoffice, Integrationen einmal „Mit Google verbinden“ und bei Google mit **info@thatsit.marketing** anmelden. Die Verbindung gehört dem Büro, alle Buchungen landen in diesem Kalender

### Resend einrichten

Absenderdomain `thatsit.marketing` bei Resend verifizieren (SPF, DKIM), `RESEND_API_KEY` als Secret setzen. Absender und Antwortadresse stehen als `vars` in `wrangler.jsonc`. Ohne Schlüssel werden Mails nur protokolliert.

## Designsystem: Tokens, Schriften, Typoskala

Alle Werte in `src/styles/tokens.css`, abgeleitet aus dem Branding Guide.

* Farben: Schwarz `#0E0E0E`, Orange `#DC9832`, Weiß. Neutraltöne `--n-050` bis `--n-900`. Semantik Erfolg `#2F8F5F`, Fehler `#C4382C`, Info `#2B6CB0`
* Orange ist Akzent (etwa 5 Prozent): orangener Punkt hinter Überschriften, primärer Button, aktive Navigation. Keine Tints oder Shades, Hover über Opacity 0.88
* Schriften, selbst gehostet in `public/fonts/`: League Spartan (variabel, Überschriften 900), Montserrat (variabel, Fließtext), Barlow Condensed 300 und 500 (gesperrte Labels und Buttons)
* Typoskala: Display bis 64px, H1 32 bis 48px, H2 26 bis 36px, H3 22px, H4 18px, Body 16px, Labels 14px mit 0.4em Sperrung
* Form: eckig, Radius 2px für UI, 0px für Markenflächen, Pillen nur für Status
* Icons: Lucide, Strichstärke 1.75, in `src/components/ui/Icon.astro`
* Backoffice Breite: Inhalt bis 1840px, Formularseiten (Einstellungen, Integrationen) ab 560px pro Karte nebeneinander. Verfügbarkeit: ab 1800px Wochenzeiten links und Kalender rechts, ab 1380px Kalender oben und Wochenzeiten neben Ausnahmen, darunter einspaltig
* Logo Let's Meet: überall kompakt ohne Unterzeile (Seitenleiste, Seitenleiste, Login, Mailkopf mit `letsmeet-kompakt-weiss.png`). ## Formulare und Datenfluss

Buchung (`POST /api/buchen`, JSON):
1. Honigtopf `website` und Mindestzeit 2,5 Sekunden, Bots bekommen Erfolg ohne Wirkung
2. Turnstile Prüfung (nur wenn `TURNSTILE_SECRET_KEY` gesetzt). Im Browser lädt `buchung.ts` das Skript erst im Formularschritt und rendert unsichtbar. Fehlt beim Absenden noch das Token, kommt die Meldung „Die Sicherheitsprüfung läuft noch“ statt einer abgelehnten Buchung. Das Feld darf nie die ID `turnstile` tragen: der Browser macht sie als `window.turnstile` verfügbar und das Skript würde nie geladen
3. Serverseitige Validierung, Fehler feldbezogen (422)
4. Slot wird erneut gegen Regeln, Buchungen und Google geprüft (409 wenn weg)
5. Speichern in D1, danach Doppelbuchungsschutz über die rowid Reihenfolge
6. Gast ins Kontaktbuch (`kontaktAusBuchung`, über die E Mail, Telefon wird ergänzt, ein entfernter Kontakt kommt zurück)
7. Google Termin mit Meet Link, danach im Hintergrund Mails an Gast und Gastgeber mit ICS Anhang und Webhook

Slotberechnung: Wochenregeln oder Tagesausnahme in der Zone des Gastgebers, Raster, Dauer, Puffer davor und danach, Mindestvorlauf, Buchbarkeit in Tagen, Tageslimit pro Terminart, alle bestätigten Buchungen des Gastgebers, Google Termine (live über `events.list`, je 30 Minuten Puffer; ist Google nicht erreichbar, gilt der letzte Abgleich aus `google_termine`).

Abgleich Google Kalender (`googleAbgleich` in `google.ts`): Der Cron holt alle 10 Minuten die Termine des Büros von 14 Tagen zurück bis 120 Tage voraus und ersetzt sie in `google_termine` (Titel, Zeit, ganztägig, blockiert, Ort, Link zu Google). Einträge älter als 30 Tage fallen weg. Zusätzlich sofort nach dem Verbinden, beim Wechsel der Kalender ID, per Knopf unter Integrationen und beim Öffnen des Kalenders, wenn der letzte Stand älter als 15 Minuten ist. Stand und Fehlergrund stehen in `nutzer.google_abgleich_am` und `google_abgleich_fehler`. Fehlerantworten der Calendar API übersetzt `googleApiFehler` in Klartext (API im Cloud Projekt nicht aktiviert, Kalender Berechtigung fehlt, Kontingent, Kalender ID unbekannt, Zugang abgelaufen), ebenso eine abgelehnte Token Erneuerung (`invalid_grant`, etwa nach 7 Tagen bei App Status „Testen“). Beim Trennen werden alle abgeglichenen Termine gelöscht. Blockierend sind Termine mit Uhrzeit, nicht blockierend ganztägige Einträge, abgelehnte Termine, Status „Verfügbar“ und Titel mit „Briefkasten“. Abgesagte Termine werden nicht übernommen.

Arbeitsabläufe (seit 2026-10-29, ersetzen die Erinnerungen in `terminarten.erinnerungen`): Tabelle `arbeitsablaeufe` (Name, `ausloeser`, `versatz_min`, `aktion`, `empfaenger`, `betreff`, `ueberschrift`, `text`, `alle_terminarten`, `aktiv`), Zuordnung in `arbeitsablauf_terminarten`, Versand je Buchung höchstens einmal in `arbeitsablauf_versand` (Status `gesendet`, `entfallen`, `fehler`). Auslöser: `nach_buchung` (sofort oder 30 Min bis 48 Std danach, auch bei Umbuchung), `vor_beginn` (7 Tage bis 15 Min), `nach_ende` (direkt bis 7 Tage), `bei_absage` und `nicht_erschienen` (sofort). Aktionen: `mail_gast`, `mail_buero` (info@), `mail_an` (bis fünf Adressen, Antworten an den Gast). Sofortige Abläufe laufen im Hintergrund bei Buchung, Absage und beim Markieren als nicht erschienen, zeitversetzte im Cron. Regeln im Cron: Fällt der Zeitpunkt vor die Buchung oder mehr als 15 Minuten vor das Anlegen des Ablaufs, entfällt die Mail. Sind mehrere Erinnerungen an den Gast gleichzeitig fällig, geht nur die kürzeste raus. Nach Ende und verzögert nach Buchung gilt ein Fenster von zwei Tagen, nach Ende nicht bei „nicht erschienen“. Fehler im Cron werden beim nächsten Lauf neu versucht. Platzhalter: `{vorname}`, `{name}`, `{email}`, `{telefon}`, `{terminart}`, `{datum}`, `{uhrzeit}` (Beginn), `{wann}` („gleich“, „in einer Stunde“ oder „am Montag, 3. November“), `{dauer}`, `{ort}`, `{meeting_link}`, `{verwalten_link}`, `{buchen_link}`, `{absagegrund}`, `{nachricht}`. Zeilen der Form „Label: {leer}“ fallen weg. Unter dem Text hängt die Mail automatisch Termindaten und Knöpfe an (Gast vor dem Termin: Zum Meeting, Umbuchen oder absagen; danach: Neuen Termin buchen; Büro und andere: Im Backoffice öffnen). Bestätigung und Absage mit ICS gehen weiter fest an Gast und Büro. Standardabläufe aus Migration 0008: „Erinnerung 24 Stunden vorher“, „Erinnerung 1 Stunde vorher“, „Nicht erschienen: neue Zeit anbieten“, alle für alle Terminarten. Die Spalten `terminarten.erinnerungen`, `erinnerung_std`, `buchungen.erinnerungen_gesendet`, `erinnerung_gesendet` sind veraltet und werden nicht mehr gelesen.

Kontaktbuch (`kontakte`): Ein Kontakt je E Mail (Teilindex, Kontakte ohne E Mail sind erlaubt). Quellen: Buchung, Gäste im Google Kalender des Büros (beim Abgleich, ohne Teammitglieder, Räume und Absagen, `google_termine.gaeste`), CSV Import (Spalten wie im Calendly Export: Name oder Vorname und Nachname, E Mail, Telefon, Unternehmen, Notiz, Datum des letzten Meetings, Trenner Semikolon, Komma oder Tab, vorhandene Kontakte werden nur ergänzt) und von Hand. Letztes Meeting = spätester Beginn aus bestätigten, erschienenen Buchungen, Google Terminen mit dem Kontakt als Gast und dem gespeicherten `letztes_meeting` (hält Google und Import fest, weil `google_termine` nach 30 Tagen aufgeräumt wird). Nächstes Meeting = frühester kommender Termin aus Buchungen und Google. Entfernen blendet Kontakte mit E Mail nur aus (`ausgeblendet = 1`, Telefon, Unternehmen und Notiz werden geleert), damit der Google Abgleich sie nicht wieder anlegt.

Umbuchen: Gast öffnet die Buchungsseite mit `?umbuchen={id}`. Die alte Buchung zählt nicht als belegt, wird nach der neuen Buchung storniert (`storno_grund = Umgebucht`, Verweis `umgebucht_zu`).

Anmeldung Backoffice: Passwort als PBKDF2 SHA256 (100.000 Iterationen), Sitzung als HMAC signiertes Cookie `lm_sitzung` (HttpOnly, SameSite Strict, 8 Stunden), Sperre 15 Minuten nach 5 Fehlversuchen, CSRF Schutz über Astro `checkOrigin`. Der Google Rückruf liegt außerhalb von `/api/app`, weil das Strict Cookie bei der Rückleitung von Google nicht mitkommt. Die Zuordnung läuft über einen signierten state mit eigenem Zweck, er ist nie als Sitzung gültig. Der Rückruf leitet danach nicht per 302, sondern über eine kleine Seite mit meta refresh weiter, sonst zählt die ganze Kette als von Google ausgelöst und das Strict Cookie fehlt auch auf `/app/integrationen` (Folge: Loginmaske). Fehler landen als `?google_fehler=` mit Code (`abgelehnt`, `state`, `kein_refresh`, `scope` (Kalender Häkchen bei Google nicht gesetzt), `invalid_client`, `invalid_grant`, `redirect_uri_mismatch`, `speichern`) und werden unter Integrationen im Klartext erklärt. Client ID und Secret werden vor der Nutzung getrimmt.

Webhook Ereignisse: `buchung.erstellt`, `buchung.umgebucht`, `buchung.storniert`, `test`. Header `x-letsmeet-signatur` = HMAC SHA256 des Rohkörpers mit dem Signaturschlüssel.

### Playbooks: persönlicher Link, Flipbook, Leads (seit 2026-10-29)

Ablauf: Formular auf einer der vier Playbook Landingpages, deren `/api/kontakt` ruft serverseitig `POST /api/playbook/anfordern` (Bearer `PLAYBOOK_SCHLUESSEL`, JSON `playbook` = `website|social|recruiting|gastro`, `name`, `email`, `telefon`, `unternehmen`, Timeout 6 Sekunden). Let's Meet legt den Kontakt an oder ergänzt ihn (`quelle = playbook`, Herkunft „Playbook angefordert“), schreibt eine Zeile in `playbook_zugaenge` (ID 24 Byte Zufall als Geheimnis im Link, `gueltig_bis` 14 Tage, `PLAYBOOK_GUELTIG_TAGE` in `playbooks.ts`, die Landingpages nennen die Frist in der Mail) und antwortet `{ link, gueltigBis }`. Die Landingpage schickt den Link in der Bestätigungsmail („Playbook ansehen und herunterladen“). Fehlt der Schlüssel, ist Let's Meet nicht erreichbar oder liegen für das Playbook noch keine Dateien vor (`link: null`, Lead wird trotzdem mit `link_versendet = 0` erfasst), nimmt die Mail den festen Downloadlink der Landingpage. Gezählt werden Aufrufe (`aufrufe`, erstmals, zuletzt) und Downloads (`downloads`). Zugänge fallen 12 Monate nach Ablauf weg (Cron, `playbookZugaengeAufraeumen`). Gespräch je Playbook: Website = `/strategiegespraech-webseite`, Social Media und Gastro = `/strategiegespraech-social-media`, Recruiting = `/strategiegespraech-recruiting`, Knopf vorausgefüllt über das Fragment mit `quelle=playbook <schluessel>`.

Dateien: `public/playbook-dateien/{schluessel}/playbook.pdf` und `seite-001.webp` usw., Liste in `src/daten/playbook-dateien.json` (Seiten, Pixelmaße, PDF Größe, Stand). **Nie direkt erreichbar:** `wrangler.jsonc` setzt `assets.run_worker_first` für `/playbook-dateien/*`, `src/worker.ts` antwortet dort 404, ausgeliefert wird nur über `/playbook/{id}/...` per `env.ASSETS.fetch` nach Prüfung des Zugangs. **Neues oder geändertes Playbook:** Rohdatei in den Ordner `playbook-quelle/` legen (steht in `.gitignore`), dann `python scripts/playbook-vorbereiten.py <schluessel> playbook-quelle/<datei>.pdf`. Braucht nur Python 3.10+ mit `pip install pikepdf pymupdf pillow`, läuft auf Windows, Mac und Linux (seit 2026-10-29 ohne poppler und ImageMagick). Das Skript verkleinert Bilder in der PDF mit pikepdf, bis sie unter 8 MB liegt (Text und Links bleiben, bei Bildern mit Transparenz wird nur die Farbe JPEG, die Maske bleibt verlustfrei; erreicht keine Stufe 8 MB, weil der Rest Vektorgrafik ist, nimmt es die beste Bildqualität, die höchstens 25 Prozent über der kleinsten Fassung liegt; eine reine PyMuPDF Komprimierung war getestet und drückte die Bilder zu stark), Cloudflare nimmt höchstens 25 MiB je Datei, rendert die Seiten mit PyMuPDF als WebP 1600px und trägt sie in die JSON ein. Am Ende tauscht das Skript über `scripts/playbook-qr.py` die QR-Codes im Playbook gegen den Link zum passenden Gespräch (Originale zeigten auf Calendly, Zuordnung wie `PLAYBOOKS`, Pakete zusätzlich `opencv-python-headless qrcode`). Liegt der Code als eigenes Bild in der PDF, wird nur dieses Bild ersetzt, sonst kommt der neue Code deckend darüber; dazu ein klickbarer Link, danach neu gerenderte Seitenbilder und Prüfung per QR-Leser. Danach `public/playbook-dateien/` und `src/daten/playbook-dateien.json` committen und nach `main` pushen, Workers Builds deployt. Stand 2026-10-29: alle vier hinterlegt. Gastro (51 Seiten, 20,2 auf 7,2 MB verkleinert), Social Recruiting (48 Seiten, 5,1 MB), Website Conversion (31 Seiten, 8,2 MB), Social Media (55 Seiten, 34,6 auf 12,5 MB verkleinert, Bilder bis 1600 Pixel, Qualität 78; rund 9 MB davon sind Vektorgrafik der Seiten). Die Rohdateien gehören nicht ins Repo.

Name in der PDF eindrucken ist bewusst nicht gebaut: geht mit `pdf-lib` im Worker, kostet aber bei 50 Seiten und 7 MB spürbar CPU je Download (Free Plan 10 ms) und lässt sich nicht zwischenspeichern.
